# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Django 5.1 management system for a multi-branch car-wash business ("AutoDash"). Tracks customers/vehicles, services rendered, subscriptions, loyalty, commissions, expenses, sales targets, bookings, maintenance, and a daily worker scorecard. Heroku-deployable (see `Procfile`).

## Commands

A virtualenv lives at `.venv/`. Activate it before running anything:
- PowerShell: `.\.venv\Scripts\Activate.ps1`
- Bash: `source .venv/Scripts/activate`

Common commands (run from repo root, where `manage.py` lives):
- Install deps: `pip install -r requirements.txt`
- Dev server: `python manage.py runserver`
- Migrations: `python manage.py makemigrations` then `python manage.py migrate`
- Shell: `python manage.py shell`
- Create superuser: `python manage.py createsuperuser`
- Collect static (production): `python manage.py collectstatic --noinput`
- Run all tests: `python manage.py test autodash_App`
- Single test: `python manage.py test autodash_App.tests.test_revenue_consistency.RevenueConsistencyTest.test_revenue_matches_orders_today`

Custom management commands (`autodash_App/management/commands/`):
- `python manage.py seed_scorecard` — upsert scorecard categories/criteria from the spec; `--reset` wipes existing scorecards first.
- `python manage.py dedupe_revenue` — one-shot cleanup that drops duplicate `Revenue` rows per service order, keeping the oldest.
- `python manage.py repair_commission_cache [--dry-run] [--fix-dates]` — recomputes each job's cached `commission_amount` from the `Commission` rows that actually exist. Never changes a `Commission` amount, so no payout is restated; `--fix-dates` additionally re-dates rows onto their job's date, which does move figures between periods.
- `python manage.py diagnose_commission [--days N | --start/--end] [--branch ID]` — read-only reconciliation of a period's `Commission` rows against the currently configured rates, attributing the gap to a rate edited after the jobs were logged, on-credit work, re-dated rows, cross-branch workers, or legacy rows.
- `python manage.py cleanup_bill_settlement_expenses` — one-shot cleanup that deletes legacy `[Bill Settlement]` `Expense` rows; bill payments now live only on `DailyPaymentTarget`, so the mirrored expenses double-counted in P&L. `--dry-run` reports without deleting.

## Configuration

Settings use `python-decouple` and read from a `.env` file at repo root. Keys actually consumed:
- `SECRET_KEY`, `DEBUG`, `ALLOWED_HOSTS` (comma-separated CSV)
- When `DEBUG=False`: `DATABASE_URL` (Postgres, parsed by `dj-database-url` with `ssl_require=True` and `conn_max_age=600`; `psycopg2` is the driver). Heroku Postgres provides `DATABASE_URL` automatically. The individual `DB_*` keys are no longer used.
- `SMS_API_KEY` — used by `autodash_App/helper.py` for the usmsgh SMS gateway

`DEBUG=True` uses the bundled `db.sqlite3`. Heroku `Procfile` runs `python manage.py migrate` on release and `gunicorn autodash_management.wsgi` for `web`. Python is pinned to 3.12 for the Heroku build via `.python-version`.

**SMS is enabled**: `autodash_App/views.py` imports `send_sms` / `send_sms_club` from `.helper` and calls them across the service, subscription, and booking flows. To disable temporarily, stub these out rather than deleting call sites.

## Architecture

Single Django project `autodash_management` with one app `autodash_App` doing essentially everything. All URLs live in `autodash_App/urls.py`; the project urlconf only mounts the app, the admin, and password-reset views.

### Auth & access control

- Custom user model: `autodash_App.CustomUser` (`AUTH_USER_MODEL`). Roles: `worker` or `customer`. Login is by `phone_number` (stored as `username` for workers — see `auth/auth_views.py`).
- `CustomUser.approved` gates login; unapproved users are bounced from `login_page`.
- Workers have a `Worker` profile (`user.worker_profile`). A worker with `is_branch_admin=True` is a branch-level admin.
- `decorators.staff_or_branch_admin_required` (at repo root) is the standard gate for "elevated" views — allows `is_staff`/`is_superuser` OR branch admins. Use it for any new admin/branch-admin view rather than `@staff_member_required` alone.
- `decorators.worker_or_elevated_required` (same file) is the looser gate for shop-floor pages any worker with a branch may reach — currently the Utilities views. It only controls who gets through the door; the view must still scope reads and writes to the user's own branch.
- Branch scoping pattern in `views.py`: `_get_admin_branch(request)` and `_get_user_branch(request)`. Branch admins are forced to their own branch; staff/superusers can pick via `?branch_id=` / `?branch=`. Follow this pattern when adding branch-scoped reports — never trust `request.GET['branch_id']` for non-staff.

### Domain model (`autodash_App/models.py`, ~1830 lines)

Read this file early — almost all business logic lives here. Key clusters:

- **Org**: `Branch`, `Worker` (with branch, `is_branch_admin` flag, and the per-worker daily targets `daily_orders_target` / `daily_services_target` / `daily_value_target` that feed the scorecard), `WorkerCategory` (the `service_provider=True` flag gates commission eligibility), worker-onboarding side-tables (`WorkerEducation`, `WorkerEmployment`, `WorkerReference`, `WorkerGuarantor`).
- **Catalog**: `VehicleGroup`, `ServiceCategory`, `Service` (priced per `VehicleGroup`, M2M to `Branch`, carries `commission_rate` and `loyalty_points_earned`/`loyalty_points_required`), `ProductCategory`, `Product`, `ProductStockLog`.
- **Customer**: `Customer` (with `loyalty_points` and helpers `add_loyalty_points` / `apply_loyalty`), `CustomerVehicle`, `LoyaltyTransaction`.
- **Subscriptions**: `Subscription` (template), `CustomerSubscription` (per-customer instance with `used_amount` / `sub_amount_remaining`), plus `CustomerSubscriptionTrail` and `CustomerSubscriptionRenewalTrail` audit logs. Use `autodash_App.subscription.assert_unique_active_subscription` before creating.
- **The core transaction**: `ServiceRenderedOrder` is the central "ticket" — links a `Customer` (or walk-in fields), a `CustomerVehicle`, M2M of `Worker`s, payment breakdown (`cash_paid`, `momo_amount`, `card_amount`, `subscription_amount_used`, `loyalty_points_used`), `status` (`pending`/`completed`/`canceled`/`onCredit`), and a discount. `ServiceRendered` is the line-item (one per service on the order, with `negotiated_price`). `Commission` rows are derived per-worker-per-line.
- **Commission**: a `Commission` row hangs off *either* a `ServiceRendered` (catalogue line) *or* an `OtherService` (non-catalogue job) — exactly one, enforced by the `commission_exactly_one_source` check constraint. Reports aggregate on `worker`/`date`, so both kinds are picked up without the caller knowing which is which; `Commission.source_name` and `.is_other_service` describe a row when you do need to tell them apart.
- **Revenue/money flow**: `Revenue` is the canonical "money received" record — one per completed `ServiceRenderedOrder` (or `OtherService`), kept in sync by signals (see below). `Arrears` tracks unpaid `onCredit` work — pointing at *either* a `ServiceRenderedOrder` or an `OtherService`, exactly one, enforced by the `arrears_exactly_one_source` constraint. Read a debt through `display_reference` / `display_description` / `display_customer_name` / `display_customer_phone` / `job` rather than reaching for `.service_order`, which is null for other-service debts. `Arrears.mark_as_paid()` creates the corresponding `Revenue` for whichever kind it is. `Expense` + `DailyExpenseBudget` + `WeeklyBudget` + `RecurringExpense` cover outflow. `RecurringPaymentSetup` + `DailyPaymentTarget` model recurring bills with rollover of unpaid balances.
- **Petty cash**: `PettyCashAccount` is the **single** cash float for the whole business — there is exactly one row, reached via `PettyCashAccount.current(create=False)`, carrying `low_threshold`, `is_active` and a cached `balance`. Cash is put down once and every branch spends from the same pot; the branch lives on the **movement**, not the account. Money in (top-up, manual reimbursement) has `branch=None` because it belongs to the shared pot; money out, and utility reimbursements, carry the branch they came from so each branch's draw stays countable. `PettyCashTransaction` is the movement log (`topup` / `expense` / `adjustment`), storing a positive `amount` plus a derived `signed_amount` and a running `balance_after`. The transactions are the truth; `account.recalculate()` rebuilds the cache and the whole running trail, so a back-dated or corrected row repairs everything after it. The balance is **top-ups + reimbursements (manual and utility) − `other`-type expenses**. Only an `Expense` with `expense_type=other` draws the float down: operating costs are the branch's running costs, settled elsewhere, so they hit Net Sales but never the cash tin. Auto-generated utility rows are excluded outright (and are separately reimbursed *into* the float). Reclassifying an expense between the two types moves it on or off the float automatically. Overspending is recorded, never blocked: the money really left, so the balance goes negative and the UI flags it.
- **Expense classification**: `Expense.expense_type` is `operating` or `other` (`Expense.TYPE_OPERATING` / `TYPE_OTHER`); only operating costs come off Net Sales. `Expense.is_auto_generated` marks rows the system wrote (currently utility usage) rather than a manager. The older free-text `expense_category` (`Statutory`/`Variable`) still exists and is unrelated to this split.
- **The sales chain**: `models.compute_sales_figures(branch=None, start, end)` is the one definition, shared by the admin dashboard and the remittance pages so they can't drift: `gross sales = revenue − commission`, `net sales = gross sales − operating expenses`. Returns plain floats. Use it rather than re-summing `Revenue`/`Commission`/`Expense` in a new report.
- **Utilities**: `Utility` is a metered resource per branch (electricity credit, water, generator fuel) with a `cost_per_unit`; `UtilityReading` is one day's movement, where `usage = opening_balance + purchase − closing_balance` and `opening_balance` is carried from the previous reading's `closing_balance`. A **top-up expense books itself as a purchase**: `find_utility_for_expense` matches an `Expense` to a utility when the description both reads as buying credit (`TOPUP_MARKERS` — topup / prepaid / recharge…) *and* names a utility at that branch, by its own name or one of its `topup_keywords` aliases (so "ECG Prepaid" reaches a utility called Electricity). Both conditions are required: matching on the utility name alone would turn every `[Recurring] Water` line into a water purchase. The amount lands in `auto_purchase`. `purchase` (hand-typed) is kept **only for history** — it is no longer a form field, since purchases now come from expenses; the reading form shows a disabled `purchase_display` instead, so nothing posted can invent credit. Only the closing balance is typed. `utility_reading_create` **adopts** an existing row rather than rejecting it, because a top-up expense will already have opened that day (`validate_unique` skips the utility/date pair for the same reason). The amount is kept **separate** from `purchase` so an automatic pickup can never overwrite someone's entry; `total_purchase` is the sum and is what `compute_usage` uses. `UtilityReading.save()` re-syncs the costed `Expense` (operating, auto-generated, forced onto the reading's date) and calls `propagate_forward()` so correcting an old reading repairs every later row in the trail.
- **Remittance** (replaces the old "operational targets"): `RemittanceSetup` is the per-branch daily expectation — `target_amount`, `apply_on` weekdays, and a `primary_source` of cash/momo/bank. `DailyRemittance` is one row per branch per day where `total_due = target_amount + brought_forward`, `outstanding = total_due − amount_remitted`, and `surplus = max(0, net_sales − target_amount)` is flagged but deliberately never carried into tomorrow. `net_sales` is refreshed live from `compute_sales_figures` until `is_finalized` freezes it at day rollover. `RemittancePayment` is one line of a possibly split remittance and calls `remittance.recalc()` on save and delete.
- **Targets**: `SalesTarget` (weekly/monthly per branch), `DailySalesTarget` (per branch per weekday), `WorkerDailyAdjustment` (per-worker bonus/deduction; `branch` auto-copied from the worker on save).
- **Walk-ins**: `ServiceRenderedOrder.is_walkin` + `walkin_*` fields cover unregistered customers — branch-admin/staff UIs always need to handle both `order.customer` and the walk-in fallback (`display_customer_name` / `display_vehicle_info` properties do this).
- **Bookings**: `CustomerBooking` (`booked` → `arrived` → `converted`); converting calls `mark_converted(order)` and links back to the `ServiceRenderedOrder`.
- **Other services & maintenance**: `OtherService` is a non-catalog job that now mirrors a service order's money handling — it produces `Revenue`, carries its own `commission_rate` (so `Commission` too), and has the same tender fields (`payment_method`, `cash_paid`, `momo_amount`, `card_amount`; no loyalty/subscription, since those need a registered `Customer`). `MaintenanceLog` + `MaintenanceExpense` are unrelated.
- **Scorecard**: `ScorecardCategory` (weights should sum to 1.0) → `ScorecardCriterion` (some `auto_source`'d from the worker's actuals against their own daily targets — `orders`, `services`, or `value` in GHS) → one `DailyScorecard` per worker per day with `DailyScoreEntry` rows. `DailyScorecard.recalc()` computes the weighted `final_score` in `[0,1]`; entries start at full marks and GMs deduct from there. Logic lives in `autodash_App/scorecard/scorecard_views.py` (~930 lines).
- **"Days worked" scoping**: `models.worked_days_by_worker(start, end, branch)`, `worked_days_map`, and `worked_worker_ids` define who was actually on duty — a worker appearing on a `ServiceRenderedOrder` or an `OtherService` that day, deduped so several orders count as one day. Targets and scorecard reports aggregate off these rather than off the length of the period, so someone who worked 3 days of a month is measured against 3 days of target. Use them for any new per-worker report.
- **Notifications**: `Notification` is branch-scoped (no per-user recipient). Workers/branch-admins see their own branch; superusers see all. Built by signals (see below) and surfaced via the `worker_notifications` context processor.

### Critical invariants enforced outside view code

These run automatically — be aware before touching `ServiceRenderedOrder` / `OtherService` / commission code.

- **`autodash_App/signals.py`**: `pre_save` snapshots old status; `post_save` on `ServiceRenderedOrder` upserts a `Revenue` row when status becomes `completed` and deletes it otherwise. Same pattern for `OtherService`. `CustomerBooking` and `MaintenanceLog` `post_save` create branch-scoped `Notification`s. If you change status transitions, this is what keeps `Revenue` in sync — don't write your own `Revenue.objects.create` in views. A `post_delete` on `UtilityReading` also deletes its linked `Expense` (that FK is `SET_NULL`, so without the signal the cost row would be stranded and overstate the branch's expenses).
- **`autodash_App/commission_util`**: `allocate_commission(service_rendered, discount_factor=1)` and `allocate_other_service_commission(other_service, discount_factor=1)` share one `_distribute` helper — they idempotently split the pool equally across the job's workers whose `worker_category.service_provider=True`, wipe obsolete `Commission` rows, and cache the pool on the job's `commission_amount`. Three guarantees live here and are covered by `tests/test_commission_math.py`: `split_pool` hands out leftover cents so the shares sum **exactly** to the pool (10.00 across 3 is 3.34/3.33/3.33, never 3×3.33); the cache is only ever set to what was actually written, so it can't claim money with no rows behind it; and a commission is dated from its **job**, so re-allocating an old order doesn't drag it into today. Rates go through `Decimal(str(...))` to keep binary float noise out of the pool. Call them via `ServiceRendered.allocate_commission` / `OtherService.allocate_commission`, never by creating `Commission` rows by hand. The catalogue rate comes from `Service.commission_rate`; a non-catalogue job has no `Service`, so the rate is set per job on `OtherService.commission_rate` (default 0, so an unrated job pays nothing).
- **Top-up expenses are signal-driven**: `post_save` on `Expense` finds its utility, gets-or-creates that day's `UtilityReading` and re-totals `auto_purchase`; `post_delete` and re-describing it away from a top-up both detach it. A reading created this way closes where it opened *plus* what was bought, so buying credit records **zero usage** until someone takes the real closing reading — otherwise it would book a huge phantom usage expense.
- **Petty cash is signal-driven**: `post_save` on `Expense` upserts the matching `PettyCashTransaction` (only for `expense_type=other`, skipping `is_auto_generated` rows and branches with no active float — see `_expense_draws_petty_cash`); `post_delete` returns the cash. `post_save` on `UtilityReading` upserts a **reimbursement** movement worth `reading.expense_amount` — the cash value of what was consumed is handed straight back so the branch can spend it, rather than waiting on a reimbursement run. Don't write `PettyCashTransaction` rows by hand — save the `Expense` or the `UtilityReading` and let the signal mirror it.
- **The utility expense and its reimbursement must not cancel**: a `UtilityReading` books an auto-generated `Expense` (the P&L cost) *and* a `+` petty-cash reimbursement. The expense is deliberately excluded from the float; if that exclusion is ever removed, the −X expense would cancel the +X reimbursement and the branch would be no better off — which defeats the whole feature. `tests/test_petty_cash.py` pins this.
- **`OtherService` commission and arrears are signal-driven**: `post_save` calls `OtherService.sync_commission()` and `_sync_other_service_arrears()`, and `m2m_changed` on `OtherService.workers` re-splits commission once the team is known (the worker list is saved after the row, so `post_save` alone runs too early). Commission is earned only while status is `completed` or `onCredit` — same rule as `Revenue` — and an `onCredit` job opens an `Arrears` row that is cleared if it moves off credit, though **never** once it has been settled. Views therefore don't need to touch commission or arrears when they move an `OtherService`; the catalogue path still does both explicitly in `views.py`.
- **Settling arrears goes through the job's status**: `mark_arrears_as_paid` writes the cash/MoMo split onto the underlying job and flips it to `completed`, which is what creates the `Revenue` row via the `post_save` signal. Don't also create a `Revenue` there — that was a live double-count bug on the service-order path.
- **`autodash_App/middleware.DailyTargetGenerationMiddleware`**: registered in `MIDDLEWARE`. On the first request of each day it does two things: generates `DailyPaymentTarget` rows from `RecurringPaymentSetup`, carrying forward any prior unpaid balance (overpayments become a negative `brought_forward` — i.e. a credit); and opens today's `DailyRemittance` for every active `RemittanceSetup`, first finalising yesterday's row (freezing its net sales) and carrying its unremitted balance in as `brought_forward`. Uses Django cache key `daily_payment_targets_done_<YYYY-MM-DD>` to dedupe both. Don't add a second daily-init mechanism — extend this one.
- **`autodash_App/context_processors.worker_notifications`**: registered in `TEMPLATES.OPTIONS.context_processors`. Every template gets `notif_unread_count` / `notif_latest_unread` / `notif_has_unread` filtered by the user's branch (or all branches for superusers).

### Views and URLs

`autodash_App/views.py` is ~9500 lines and holds the bulk of view code (worker-side service logging, customer-side dashboard, all admin/branch-admin reports, exports, booking flow, maintenance flow, etc.). The split-out files `auth/auth_views.py` and `scorecard/scorecard_views.py` are the only ones populated; `customer/`, `worker/`, `services/` directories exist with empty `*_views.py` placeholders — don't assume new view code belongs there unless explicitly extracting.

URL convention: admin / branch-admin routes are namespaced under `elevated/` in `autodash_App/urls.py`. Customer-only routes live under `customer/`. The root `''` route is `views.home`, which is also re-aliased as `select_branch` and `admin_dashboard` at different paths — be careful when reverse-resolving.

### Templates and static

Templates live in `autodash_App/templates/`, configured via `TEMPLATE_DIR = BASE_DIR / 'autodash_App' / 'templates'` plus `APP_DIRS=True`. Layout fragments are in `templates/inc/` and `templates/layouts/`. Custom filters: `autodash_App/templatetags/custom_filters.py` and `auth_extras.py` — `settings.py` imports `custom_filters` at module load, so breaking that module breaks Django startup.

Static files: `autodash_App/static/` (dev) collected to `BASE_DIR/assets/` (prod), served via WhiteNoise's `CompressedManifestStaticFilesStorage`. Media uploads go to `BASE_DIR/media/`.

## Conventions worth following

- `OtherService` payment splits are validated on `OtherServiceForm.clean()`: a `completed` job's cash + MoMo + card must equal `amount`, and an `onCredit` job must carry no payment at all. `payment_method` is derived in `save()` via `infer_payment_method()`, never asked for as its own input.
- `Commission.date` is a plain `DateField` (**not** `auto_now_add`) and `Commission` has unique constraints on (worker, service_rendered) and (worker, other_service) — idempotency is enforced by the database, not merely assumed by `update_or_create`.
- `ServiceRendered.save()` no longer guesses a `commission_amount` at creation. That field is a cache of what `allocate_commission` actually paid; anything else overstates on lines that were never allocated.
- The petty cash page uses `_petty_cash_scope`, **not** `_utility_scope`: with no `?branch_id` chosen staff see everything, rather than `_utility_scope`'s silent fall back to the first branch. A branch filter narrows **which movements are listed and totalled, never the balance** — there is one pot, so its balance is the same figure whatever is selected; the page says so explicitly. Non-staff stay pinned to their own branch.
- Petty cash top-ups and threshold changes are branch-admin only (`_can_manage_petty_cash`), and the POST views resolve the branch through `_petty_cash_branch_or_deny` rather than `_utility_scope` — the latter reads the branch only off the query string, so a staff POST would silently write to the wrong branch.
- Money values are `FloatField` throughout (legacy choice — don't migrate to `Decimal` ad-hoc). The one exception is `commission_util.py`, which converts to `Decimal` internally with `ROUND_HALF_UP` for the actual split math.
- When mutating a `ServiceRenderedOrder`'s workers, line prices, or discount, re-run `allocate_commission` on each affected `ServiceRendered` rather than touching `Commission` directly.
- Don't bypass the `post_save` signal by writing to `Revenue` directly except in `Arrears.mark_as_paid()` (which already does the right thing) — use `ServiceRenderedOrder.status` transitions.
- For any figure in the revenue → gross sales → net sales chain, call `models.compute_sales_figures` instead of re-deriving it, and give every new `Expense` an `expense_type` — only `operating` reduces net sales.
- Utility costs are booked by saving a `UtilityReading`, never by creating the `Expense` directly. Editing an old reading is safe: `propagate_forward()` fixes the opening balances and expenses of every reading after it.
- New "elevated" pages should be gated with `staff_or_branch_admin_required` and scoped via `_get_admin_branch` for staff or the worker's own branch for branch admins. Shop-floor pages open to plain workers use `worker_or_elevated_required` and must do their own branch scoping (see `_utility_scope` in `views.py`).
- Phone numbers are stored as dialled locally, leading zero included (e.g. `0242442147`); `helper._send` prepends `233` (Ghana) and the gateway drops the extra digit itself. `SMS_API_KEY` is sent as a `Bearer` token — without the prefix every request 401s — and the helper raises on a non-2xx or non-`success` response instead of silently looking delivered, so call sites wrap it in try/except and surface the error.
